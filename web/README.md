# Websites (Vercel)

Three Vercel projects, all on the free Hobby plan while building and testing. Hobby is for **non-commercial use only**: move a site to Vercel Pro (or Cloudflare Pages, Netlify or a VPS; the output is plain static files) before it takes payments or shows ads.

| Folder | Vercel projects | What it is |
|---|---|---|
| `app_site/` | `iwant-usa-web`, `iwant-india-web` (same folder, `SITE_COUNTRY` differs) | Landing page, legal pages, account deletion, deep-link fallbacks, `.well-known` files, seller signup / contact / waitlist forms, SEO price pages, buying guides |
| `trends_site/` | `trends-web` | Separate trends news site (Section 21.10), own domain, no app branding |
| `content/legal/` | none | Generated by `python3 legal/build.py`; read by `app_site` at build time. Do not edit by hand |
| `shared/ai_bots.json` | none | AI crawler list used by every site's `robots.txt` |
| `shared/og.mjs`, `shared/fonts/` | none | Open Graph image template and its fonts (Inter, Noto Sans Devanagari; OFL, subset), used by both sites. `Inter-*.woff2` are the same subset converted for the web: both sites self-host them at `/fonts/` (no font CDN) |
| `shared/check-dist.mjs` | none | Post-build check of `og:image` files and hreflang alternates (`npm run check:dist`) |

## Project settings (all three)

- **Framework preset:** Astro. **Install:** `npm ci`. **Build:** `npm run build`. **Output:** `dist` (already set in each `vercel.json`).
- **Root directory:** `web/app_site` or `web/trends_site`.
- **Include files outside the root directory in the build step: ON.** `app_site` reads `web/content/legal`, `web/shared` and `branding/`; `trends_site` reads `web/shared`.
- **Node.js:** 22.x. Production branch `main`; every other branch gets a preview deployment.
- **Spend management:** set a spend limit and usage alerts (Settings > Billing) so a traffic spike cannot create a bill.
- **Firewall:** turn on Bot Protection and the AI-bot rule (enforces `robots.txt`), and rate-limit form-heavy paths (e.g. 10 requests per minute per IP on `/sellers`, `/contact`, `/waitlist`, `/legal/account-deletion`).
- **Domains:** keep DNS at the registrar. `iwantusa.app` and `iwantindia.app` are placeholders, and so is the trends domain.

## Environment variables

None of these are secrets. They all end up in public HTML or `/.well-known` files. The Turnstile **secret** key belongs only in the Supabase Edge Function's secrets, never here. Every variable is listed in each folder's `.env.example`.

### `app_site`: set per project

| Variable | `iwant-usa-web` | `iwant-india-web` |
|---|---|---|
| `SITE_COUNTRY` (required) | `usa` | `india` |
| `SITE_URL` | `https://iwantusa.app` | `https://iwantindia.app` |
| `ANDROID_SHA256_FINGERPRINTS` | Play App Signing + upload key SHA-256, comma-separated | same, for the India app |
| `ANDROID_EXTRA_PACKAGES` | optional, e.g. `com.calecute.iwant.usa.stg` | optional |
| `APPLE_TEAM_ID` | 10-character team id | same |
| `APPLE_APP_ID` | numeric App Store id once live (turns on store badge + Smart App Banner) | same |
| `PLAY_STORE_LIVE` | `1` once the listing is public | same |
| `PUBLIC_TURNSTILE_SITE_KEY` | Turnstile site key for the domain | same |
| `FORMS_ENDPOINT` | `https://<usa-prod-ref>.supabase.co/functions/v1/web-forms` | `https://<india-prod-ref>.supabase.co/functions/v1/web-forms` |
| `SUPPORT_EMAIL` | optional fallback shown when forms are off | same |
| `SEO_DATA_URL` | `https://<usa-prod-ref>.supabase.co/storage/v1/object/public/public-data/seo/usa.json` (nightly SEO export) | `https://<india-prod-ref>.supabase.co/storage/v1/object/public/public-data/seo/india.json` |
| `SEO_DATA_REQUIRED` | `1` on Production only (a failed fetch fails the build, so the last good deployment stays live instead of a build without price pages) | same |
| `LEGAL_STRICT` | `1` on Production only (fails while legal placeholders remain) | same |
| `TRENDS_DATA_URL` | same bucket URL as the trends site (town pages' "What's happening"); optional | same |
| `TRENDS_SITE_URL` | optional, default `https://iwant-trends-web.vercel.app` | same |
| `REQUESTS_FEED_URL` | optional public JSON feed of recent requests per town (not built yet; leave unset) | same |

If a value is unset, the build still succeeds: `assetlinks.json` and `apple-app-site-association` get `REPLACE_WITH_...` placeholders (links will not verify), forms render disabled, and store badges say "Coming soon" and link to `/waitlist`. Each case prints a build warning.

### `trends_site`

`SITE_URL`, `SITE_NAME`, `EDITOR_NAME`, `EDITOR_EMAIL`, `PUBLIC_TURNSTILE_SITE_KEY`, `FORMS_ENDPOINT`, `TRENDS_DATA_URL` (below), and `NEWS_SITEMAP=1` only once the site qualifies for Google News. Publishing caps, the ramp level and the kill switch live in `trends_site/data/config.json`, which the admin panel owns.

`TRENDS_DATA_URL` is the trends pipeline's public bucket, e.g. `https://<ref>.supabase.co/storage/v1/object/public/trends-public/` (or its `index.json`). When it is set, `npm run build` first runs `scripts/fetch-trends-data.mjs` (the `prebuild` step), which downloads `index.json` and every `articles/<slug>.json` it lists into `.trends-remote/` (gitignored); the build then reads those **in addition to** `data/articles/` (local files win on duplicate slugs) and runs every gate below on them, unchanged. The remote index can only tighten `config.json`: its kill switch pauses publishing from its `paused_at`, and its daily cap per country applies only when lower (so `config.json` caps act as a ceiling; raise them in the repo when the admin ramps up). The build fails if the URL is not https or the index cannot be loaded or is malformed, so a broken bucket never publishes an empty site; single unreadable articles are skipped with a warning. Unset, only `data/articles/` is built.

## Local builds

```sh
cd web/app_site && npm ci
npm run build:usa        # or build:india; other variables: export them first (e.g. set -a; . ./.env; set +a)
SEO_DATA_FILE=data/seo/fixtures/usa.json npm run build:usa   # exercise the price-page gates with sample data

cd ../trends_site && npm ci
npm run build                                   # real articles from data/articles (empty by default)
BUILD_NOW=2026-10-02T00:00:00Z npm run build:fixtures   # sample articles, one per gate
TRENDS_DATA_URL=https://<ref>.supabase.co/storage/v1/object/public/trends-public/ npm run build   # plus the pipeline's bucket
```

Each build logs what it published and why everything else was skipped or set to noindex.

### Translations, Open Graph images, Lighthouse

- **Translations (hreflang):** the India site has Hindi (`/hi`, `/hi/sellers`, `/hi/waitlist`, `/hi/about`) and the USA site Spanish (`/es/...`) for those four marketing pages only. Strings are in `app_site/src/i18n/{en,hi-IN,es-US}.json` (hand-written, terms as in the app's `lib/l10n`; missing keys fall back to English) and the page bodies in `src/components/pages/`. Each version links the others with `hreflang` plus `x-default` (English), in the HTML and in `sitemap-pages.xml`. Price pages, guides, seller profiles, legal and contact pages stay English: add a translation only with real translated content, never machine-translated copies. Town and state pages also come in the state's language (see "Town pages" above; `src/i18n/{ml,ta,te,kn,mr,bn,gu,pa,or,as,ne}.json` hold only the town-page, picker and layout strings, so their pages link to English elsewhere).
- **Open Graph images:** every build renders a 1200x630 PNG per page to `/og/<page path>.png` (`app_site`: home and the translated pages in each language, city and price pages, guides, seller pages; `trends_site`: home, country pages and every article) from the template in `shared/og.mjs`, using `branding/<country>/colors.json` and the logo (`trends_site` uses its own colours, no app branding, no photos). `@resvg/resvg-js` renders; text is shaped with `harfbuzzjs` so Hindi renders correctly. With live data only indexable pages get their own image (about 50 ms each); the rest, and other pages, use `branding/<country>/web/og_image_1200x630.png` (`trends_site`: `/og/site.png`).
- **Lighthouse CI:** CI (`websites` job) builds each site with fixtures, runs `npm run check:dist`, then `npm run lhci` (`@lhci/cli` via npx; pages and thresholds in each `lighthouserc.cjs`: performance >= 0.9, accessibility >= 0.95, best practices >= 0.9, SEO >= 0.95; fixture pages are noindex by design, so they check each SEO audit except crawlability). Reports are uploaded as a build artifact. Locally, after a fixture build: `SITE_COUNTRY=usa npm run lhci` (`app_site`) or `npm run lhci` (`trends_site`); set `CHROME_PATH` if Chrome is not found (e.g. `/opt/pw-browsers/chromium-1194/chrome-linux/chrome`).

## How content gets in (and stays clean)

- **Legal pages:** edit `legal/<country>/*.md` and `legal/config.json`, run `python3 legal/build.py`, and commit. The site fills in the web-domain placeholder from `SITE_URL`.
- **SEO price pages and buying guides (`app_site`, Section 21.9):** every night at 02:40 UTC `pg_cron` calls the Supabase Edge Function `seo-export` (job `iwant-seo-export`). It runs `public.seo_export()` (aggregated, anonymised stats only: medians and quartiles over at least the threshold number of quotes and sellers, rounded; most-quoted models only when several sellers quoted them; no buyer data, no seller's own quote), checks the JSON again, uploads it to the public Storage bucket `public-data` as `seo/<country>.json` and POSTs the Vercel **Deploy Hook** stored in the function secret `VERCEL_DEPLOY_HOOK_APP_SITE` (without it the function only logs a dry run). Point `SEO_DATA_URL` at that public object URL (table above); the loader adds a `?v=<minute>` cache-buster so the rebuild never reads the CDN's previous copy. Admins can also press **Run export now** in the admin panel (SEO pages screen). A city x category page is indexable only with at least 10 quotes from at least 3 sellers in 90 days and a quote within the last 90 days (defaults; admins edit them in the panel, and the export writes them into the data file). Rows below that are built with `noindex` and left out of the sitemap. Rows with no quotes, merged towns (their quotes count for the larger area page, which lists them), and restricted or blocked categories are not built at all. The committed default files have no page rows, so nothing is published until real data exists.
  - Buying guides (`/guides/<slug>`, Article schema, `sitemap-guides.xml`) come from the same file (`guides[]`). The export only contains guides a person approved in the admin panel: `approved` ones are built as `noindex` previews and linked from nowhere; `published` ones are indexable while their last review is under 184 days old (re-review twice a year). Guide pages show the reviewer date, an AI-assistance note when it applies, and the live median for their city x category. Markdown is rendered by `src/lib/markdown.ts` (no raw HTML).
  - Seller directory (`/sellers/<city>/<slug>` with LocalBusiness schema, per-city index `/sellers/<city>` linked from the city price pages, `sitemap-sellers.xml`) comes from `sellers[]`, which holds only sellers who turned on "Show my business on the website" in the app (account screen). A profile is indexable and in the sitemap only with a track record: a rating (exported from 3 reviews), a response time (exported from 5 quotes sent) or a completed order (`completed_orders`, if the export adds it), plus at least one allowed category; others are built `noindex`. Sellers without a city are not built; merged towns list under the larger area. Pages show no contact details (description sentences with a phone number, email or link are dropped), no quotes and no buyer data. "Get a quote from this seller" links to the app's `/s/<id>` when the export carries the seller `id`, else to the store badges.
  - Data format: `SeoData` in `src/lib/seo.ts`; examples in `data/seo/fixtures/` (`SEO_DATA_FILE=data/seo/fixtures/usa.json npm run build:usa`).
- **Town pages, state pages and the town picker (`app_site`):** one page per populated place: about 7,000 towns in India and 17,000 in the USA, at `/<state>/<town>` (e.g. `/kerala/kochi`, `/texas/dallas`), with a state index at `/<state>` and the country directory at `/in` (both sites; the path is historic). Old `/in/<slug>` URLs of the 53 hand-curated towns are 301-redirected in `app_site/vercel.json`.
  - **Data:** `app_site/data/towns/generated/<country>.json.gz`, generated by `tool/data/build_towns.py` (Python 3, stdlib only; `python3 tool/data/build_towns.py` downloads the sources into a cache and rewrites both files; `--offline` reuses the cache). Sources, all GeoNames under **CC BY 4.0** (attribution on `/legal/open-source#data` and under every postal-code list): `cities.json` (npm, the GeoNames "cities500" export: populated places, admin1/admin2 names), `cities-500-structured` (npm: population, alternate and native-script names, feature codes) and the GeoNames postal-code dumps `IN.zip` / `US.zip` (mirror: github.com/zauberware/postal-codes-json-xml-csv). The script matches places to post offices (India: post-office name in the same district, else the nearest office within 5 km, shown as "nearest PIN"; USA: USPS place name), takes areas from post offices (towns over 100,000 people) and GeoNames neighbourhoods, gives duplicate names in one state a district/county suffix, and merges the hand-curated towns in `data/towns/<country>.json` (they keep their slug, name, areas and aliases; the build fails if one goes missing). Rerun it and commit the two `.json.gz` files to refresh.
  - **Page:** breadcrumb country › state › district › town, store badges with campaign `town_<slug>`, recent requests (only when `REQUESTS_FEED_URL` is set, below), allowed categories, prices quoted (only from the SEO export, only rows that pass its thresholds), areas and PIN/ZIP codes, how it works, "Run a shop in <town>?", up to 5 nearby towns with straight-line distances and a small map, "What's happening" (below), FAQ, links up to the state and the country. Sections without real data are left out. Population is shown only as a band. A page is indexable when it has at least one town-specific fact (postal codes, areas, district or population); the few without any are `noindex`.
  - **Languages:** every town and state page also exists in the state's language: India `/<lang>/<state>/<town>` with Hindi (`/hi`, Hindi-speaking states, Delhi, J&K, Ladakh, Arunachal, Andaman), Malayalam `/ml`, Tamil `/ta`, Telugu `/te`, Kannada `/kn`, Marathi `/mr` (Maharashtra, Goa), Bengali `/bn`, Gujarati `/gu`, Punjabi `/pa`, Odia `/or`, Assamese `/as`, Nepali `/ne` (Sikkim); English only for Manipur, Meghalaya, Mizoram, Nagaland. USA: Spanish `/es/<state>/<town>`. Only the template strings are translated (`src/i18n/<lang>.json`, `townPage.*`, `statePage.*`, `states`; hand-written); town and area names come from the data (native-script names where GeoNames has them). Each pair links the other with `hreflang` plus `x-default` (English), in the HTML and the sitemaps. Indic scripts use system fonts (no font download).
  - **Scale:** fully static. Local build times (this machine): India about 40 s for 14,000 pages, 345 MB; USA about 75 s for 34,400 pages, 660 MB; both below the limits where on-demand rendering would be needed. OG images: one per state plus the curated towns (`/og/<state>.png`); not one per town. Sitemaps: `sitemap-states.xml` and `sitemap-towns-<n>.xml` (10,000 URLs per file, each with its hreflang set), listed in `sitemap.xml`. `TOWNS_LIMIT=<n>` builds only the curated towns plus the `n` largest others (quick local builds; CI builds everything).
  - **Picker:** every page has a "Choose your town" link to `/in` in the header (works without JavaScript). With JavaScript it opens a dialog; the town list `/towns-index.json` (about 300 KB gzipped for the USA) is fetched only when the dialog opens, PIN/ZIP lookups `/towns-postal.json` only when digits are typed. Search by name, native name, old name or PIN/ZIP; "Use my location" (browser geolocation, only on click; nearest town computed in the browser, nothing sent anywhere) and a map (Leaflet from npm, loaded only when opened; dots for the larger towns, a click snaps to the nearest of all; OpenStreetMap tiles, hence `https://tile.openstreetmap.org` in the CSP `img-src` and `geolocation=(self)` in `Permissions-Policy`). The chosen town is kept in `localStorage` (`iwant.town`, `{path: "<state>/<town>", name}`) and shown in the header and on the home page; nothing redirects.
  - **Recent requests:** with `REQUESTS_FEED_URL=https://...` the page includes a hidden section that fetches `<url>/<state>/<town>.json` (`{items: [{title, category?, area?, created_at?}]}`) in the browser and shows up to 6 items, rendered as text; with no items or any error it stays hidden. The URL must be same-origin or `*.supabase.co` (CSP `connect-src`). Unset (today): no section, no request.
  - **What's happening:** headlines from the trends site at four levels (the town, its state, the country, the world), each with one line per perspective and a link to the full article on the trends site (`TRENDS_SITE_URL`, default `https://iwant-trends-web.vercel.app`). Read at build time with the trends site's own loader and gates from `trends_site/data/articles/` and, when `TRENDS_DATA_URL` is set, the pipeline bucket (the `prebuild` step downloads it; a failed download only warns here). Only articles the trends site publishes as indexable and from the last 30 days; a level with nothing is hidden, and the whole section when all are empty. World news needs the optional article field `scope` (`supabase/API.md` section 13). `TRENDS_INCLUDE_FIXTURES=1` with `TRENDS_DATA_DIR=../trends_site/data/fixtures` and `BUILD_NOW` shows sample articles locally.
- **Trends articles (`trends_site`, Section 21.10):** the pipeline (`supabase/functions/trends-*`, see `supabase/API.md` section 13) writes one JSON file per article to the `trends-public` bucket read through `TRENDS_DATA_URL` (articles may also be committed to `data/articles/`; see `data/fixtures/` for the format) and calls the project's Deploy Hook (`VERCEL_DEPLOY_HOOK_TRENDS_SITE`). The build rejects any article that fails the gates: at least 2 independent sources; sensitive topics only with a recorded human approval; originality (upstream check plus local n-gram overlap and long-quote checks); fact consistency; at least 250 words with a local angle and what to watch next; balanced, non-partisan perspectives; and the kill switch plus per-country daily and hourly caps. Superseded articles and articles whose traffic died after the trend ended are set to `noindex`. Articles may carry the optional field `scope` (`local | state | country | world`); this site ignores it, and the main site's town pages use it to file country and world news (`supabase/API.md` section 13).

## Form endpoint contract (Edge Function not in this folder)

Forms `POST` JSON to `FORMS_ENDPOINT`:

```json
{ "form": "seller_signup | contact | waitlist | account_deletion | trends_contact",
  "country": "usa | india", "page": "/sellers", "submitted_at": "ISO",
  "fields": { "...": "..." }, "consents": [{ "key": "consent_email", "text": "exact wording shown" }],
  "honeypot": "", "turnstile_token": "..." }
```

The function must do the following:

- Verify `turnstile_token` server-side with the Turnstile secret.
- Drop any request whose `honeypot` is not empty.
- Rate-limit per IP and answer `429` with `Retry-After` when the limit is hit.
- Allow CORS from the site's origin only.
- Store consent text and timestamps in `consents`.
- Run double opt-in for the waitlist; nothing is sent before the person confirms.
- Confirm account-deletion requests by OTP to the registered phone.

Buyer outreach stays consent-based: the forms only collect people who opt in themselves.

If the function is served from a custom domain instead of `*.supabase.co`, add that domain to `connect-src` in the CSP in `vercel.json`.
